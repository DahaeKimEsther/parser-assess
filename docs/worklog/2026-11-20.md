# 2026-11-20

**한 줄 요약**: LiteParse 평가 계획을 "직접 만든 샘플" 대신 "ParseBench-2에서 쉬운 문서부터 어려운 순서"로 다시 짜고, 공식 도구 `parse-bench`를 설치해 실행 방법과 결과 형식을 확인하는 T1을 진행했다. 데이터를 받는 단계에서 멈췄고 내일 이어간다.

## 한 일

- 계획 재작성(리뷰 2판): 직접 만든 샘플로 구조 요소를 재는 계획을 버리고, ParseBench-2 문서를 우리 복잡도 점수로 쉬운 순서대로 정렬해 LiteParse 공식 점수를 함께 보는 `assess` 계획으로 바꿨다. 작업은 T1~T5로 나눴다.
- 직접 만든 샘플 탐침(첫 T1): 표/헤딩/목록/2단/한국어 PDF 7건을 만들어 LiteParse 출력을 확인했다. 깨끗한 합성 PDF에서는 구조가 제대로 나왔고, 짧은 정상 페이지가 스캔으로 잡히는 sparse-text 오탐도 다시 확인했다. 합성 샘플이라 실제 품질을 보여 주지는 못한다는 점이 계획 변경의 계기가 됐다. 스크립트(`scripts/make_samples.py`)는 아직 커밋하지 않았다.
- `parse-bench` 설치와 옵션 확인: `uv tool install "parse-bench[liteparse]"`로 전역 도구 환경에 설치했다. `pyproject.toml`은 바뀌지 않는다. `run --help`로 옵션을 확인했고(`--test`, `--group`, `--dataset`, `--output_dir`, `--open_report`, `--force`), 파이프라인 목록에 `liteparse_markdown`이 있음을 확인했다.
- 첫 실행(v1 `--test`, 12개 PDF)은 전부 실패했다. parse-bench가 LiteParse를 `lit` 실행 파일로 호출하는데 PATH에 없었다. `LITEPARSE_BIN` 환경변수로 경로를 지정하면 된다.
- v2 전체 데이터셋 다운로드(9,215개 파일, 예상 3시간 이상)를 `--test`를 빼고 시작해서 중단하고, 받다 만 폴더를 지웠다.

## 결정과 이유

- **공식 파이프라인과 채점기를 그대로 쓴다(D4 A안)**: `assess`는 우리 복잡도 점수로 정렬하고 공식 점수를 보여 주기만 한다. 채점기를 직접 만들 필요가 없고, 공식 결과와 비교할 수 있다. 공식 설정(markdown 출력, OCR 끔)이 우리 설정과 같음을 확인해서 근거가 생겼다. 버린 대안: 우리 `LiteParseParser`를 parse-bench 파이프라인으로 등록하는 B안(버전이나 설정이 다르면 그때 올린다).
- **직접 만든 샘플과 `truth.json` 구조를 버렸다**: 처음 리뷰에서는 정답을 스크립트와 채점기 두 곳에 두면 어긋난다는 이유로 PDF 옆에 `*.truth.json`을 두고(D2), 채점기를 짓기 전에 최소 샘플로 LiteParse 출력부터 보기로(D3) 했다. 그런데 샘플은 깨끗해서 LiteParse가 잘 읽는 게 당연하고 실제 문서 품질을 보여 주지 못한다. ParseBench-2는 정답과 기준 마크다운이 이미 들어 있어 D2의 `truth.json`이 필요 없어졌다. 계획 파일 수도 8개에서 5개로 줄었다.
- **parse-bench는 프로젝트 의존성에 넣지 않는다**: 전역 도구(`uv tool`)로 설치한다. 외부 평가 도구라 저장소 코드가 import하지 않고, `liteparse>=2.19.0` 의존성과 충돌할 일이 없다.
- **T4에서 CLAUDE.md의 개발 명령어에 parse-bench 설치 명령을 적는다**: 선택 의존성처럼 설치 방법이 문서에 있어야 평가 결과를 만드는 방법을 알 수 있다.
- **긴 명령은 짧은 줄이나 변수(splatting)로 안내**: 터미널에 붙여 넣을 때 긴 줄이 끊겨 명령이 깨지는 일이 반복됐다.

## 막힌 점 / 다음 할 일

- 확인된 것: parse-bench 2.1.3. 결과는 `output/liteparse_markdown/`에 `_summary.json`, `_errors.json`, `_metadata.json`으로 생기고 문서 id는 `카테고리/파일이름` 형태다(v1 기준). `--dataset` 기본값은 v1(`parsebench`)이고 v1 `--test`는 한 페이지짜리 PDF 12개(chart/layout/table/text 계열)다.
- ParseBench-2는 LlamaIndex가 올린 v1의 후속 버전이다(서브에이전트 조사, 페이지 일부는 요약에 의존). 4,317페이지, 13개 하위 세트이고 PDF마다 정답과 기준 마크다운이 들어 있다. v1과 점수를 비교할 수 없다. `--dataset parsebench-2`는 설치된 parse-bench 2.1.3이 받는 값임을 확인했다(HuggingFace `llamaindex/ParseBench-2`로 풀려 다운로드가 시작됐다). `--test`가 v2에서도 작은 부분만 받는지는 아직 확인하지 못했다.
- 남은 파일: `data/parsebench/` 아래의 v1 `--test` 데이터(`data/test`)와 실패한 실행 결과(`output/liteparse_markdown`). v2 `--test`가 같은 폴더를 쓸 수 있어서 v2 실행 전에는 지우지 않는다.
- 내일: v2를 `--test`로 실행해 결과 폴더 형식, 문서 id, LiteParse 버전을 확인하고 T1을 마친다. 그다음 T2(`assess` CLI), T3(테스트), T4(CLAUDE.md), T5(복잡도 가중치 보정).
- 확인할 것: parse-bench는 `lit`을 json 형식으로 호출해 변환하는 것으로 보이는데, 우리 라이브러리의 markdown 출력과 같은지(다르면 B안 검토). v2에 한국어 문서가 있는지(독일어, 일본어, 중국어 파일 이름은 보이나 한국어는 언급이 없다). 한 페이지짜리 문서에서 sparse-text 오탐이 복잡도 정렬을 왜곡하는지.
- 정리할 것: 미커밋 `scripts/make_samples.py`와 `data/samples/`를 남길지 지울지 정한다. 한국어 샘플은 v2에 한국어가 없으면 쓸모가 있다.
