# Decisions

사용자가 확정한 결정만 적는다. 계획이나 설계를 세우기 전에 먼저 읽고, 여기서 접은 항목은 다시 꺼내지 않는다.

## 사용 규칙

- 새 결정은 사용자가 확정한 뒤에만 적는다. 제안이나 추측은 적지 않는다.
- 바뀐 결정은 지우지 않고 `폐기됨`으로 표시하고, 대체한 결정을 가리킨다.
- 항목이 20개쯤 넘으면 `docs/decisions/`로 나눈다.

## 항목 형식

```
### YYYY-MM-DD 결정 한 줄
- **결정**: 무엇으로 정했는가
- **이유**: 왜 그렇게 정했는가
- **하지 않기로 한 것**: 접은 대안, 지금은 신경 쓰지 않기로 한 것
```

## 목록

### 2026-11-24 저장소를 파서 평가 전용(parser-assess)으로 좁힌다
- **결정**: 저장소 이름은 `parser-assess`, 패키지명은 `parser_assess`로 한다. 처리 파이프라인을 제거하고 평가 로직(복잡도 점수, LiteParse 엔진, `complexity` 명령)만 남긴다. 패키지명이 이미 평가를 뜻하므로 `assess/` 하위 폴더는 두지 않는다.
- **이유**: 목표가 "사내 문서 RAG 전체"에서 "파서가 벤치마크에서 어느 문서까지 쓸 만한지 판단"으로 바뀌었다. 이전에 `complexity.py`를 `parser/`에 둔 이유(라우터 재사용)는 라우터가 사라져 해소됐다.
- **하지 않기로 한 것**: 문서 처리(`.md` 변환)·처리 시간 측정·라우팅, RAG 후속 단계(청킹·임베딩·검색) 확장. 이전 구현은 git 이력(`618f748` 이전 커밋)에서 되살릴 수 있다.

### 2026-11-24 공식 parse-bench 파이프라인과 채점기를 그대로 쓴다
- **결정**: LiteParse 평가는 공식 도구 parse-bench의 `liteparse_markdown` 파이프라인으로 실행하고, 채점도 parse-bench의 공식 채점 결과를 그대로 쓴다.
- **이유**: parse-bench에 `liteparse_markdown` 파이프라인이 이미 있고 채점은 규칙 기반(LLM 판정 없음)이라, 그대로 쓰면 공식 점수와 같은 기준으로 비교할 수 있다. 공개된 결과 데이터셋(ParseBench-2-results)에는 문서별 점수가 없어서 점수는 직접 돌려 얻어야 한다. [확인 필요: 확정 당시 이유와 같은지]
- **하지 않기로 한 것**: 자체 채점기.

### 2026-11-24 ParseBench-2 문서를 복잡도 점수로 정렬해 공식 점수와 함께 본다
- **결정**: 직접 만든 샘플 대신 ParseBench-2 문서를 쓴다. 우리 복잡도 점수(`complexity.py`)로 문서를 쉬운 순서대로 정렬하고, 같은 문서의 공식 점수를 한 표에 합쳐 어떤 구조 요소까지 쓸 만한지 본다.
- **이유**: ParseBench-2에는 문서별 난이도 필드가 없다(`tags`의 `hard`/`easy`는 일부 하위 세트에만 있고 정의도 없다). 그래서 PDF 구조 특징(스캔, 다단, 표, 그림)으로 직접 점수를 계산해 정렬한다. 직접 만든 합성 샘플은 실제 품질의 근거가 되지 못한다.
- **하지 않기로 한 것**: 하위 세트(subset) 단위 정렬(순서가 주관적), 여러 파서 출력을 재채점하는 컨센서스 난이도(결과 데이터셋 4.7GB, 절차 미확인).

### 2026-11-24 OCR은 끄고 평가한다
- **결정**: LiteParse는 `ocr_enabled=False`로 고정해 쓴다. 스캔 PDF는 본문이 비고 `empty: true`가 붙는 것으로 신호를 삼는다.
- **이유**: 공식 벤치마크 점수(`liteparse_markdown`)가 OCR을 끈 상태로 측정되어 같은 조건이어야 비교된다. 한국어 traineddata와 첫 사용 시 자동 다운로드 동작도 확인하지 못했다.
- **하지 않기로 한 것**: OCR 버전 평가. 한국어 OCR 동작을 확인한 뒤 평가 대상 파서를 늘릴 때 다룬다.
